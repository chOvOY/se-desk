## 1. 项目背景与要解决的问题

ToB 客户沟通（无论是客户经理经营客户，还是销售工程师做方案讲解）常见痛点是：

1. **纪要散**：会议记录、微信、邮件散落，上场前很难快速变成可用结构。  
2. **准备不完整**：容易只顾讲产品，漏掉客户现状、真实需求、该追问的问题。  
3. **竞品难处理**：知道客户在比别的厂商，但缺少结构化对比，容易临场乱讲或乱贬。  
4. **多访信息丢**：同一客户第二次、第三次拜访时，上次确认的事实和未解决的问题对不上。  
5. **容易过度承诺**：把假设当事实、把未核实参数讲死，带来信任与合规风险。

本项目把「见客户前该准备什么」固化成一套**可执行的标准动作 + 本地工具**，用结构化草稿、客户名录和多访累计，提升拜访准备效率与专业度。

---

## 2. 项目定位（一句话与三句话）

**一句话：**  
服务本人客户拜访与方案沟通的会前准备工具——把纪要整理成可手改、可导出的结构化草稿，并用名录持续跟进客户。

**三句话：**

1. **是什么：** 会前备战台，不是客户侧产品。  
2. **怎么用：** 输入纪要与我方产品/方案要点 → 生成七段草稿 → 手改核实 → 合并进客户档案 → 需要时导出 PDF。  
3. **价值：** 拜访前更清楚该问什么、该讲什么、哪些不能乱讲；同一客户连续跟进时信息不丢。

## 4. 功能详解

### 4.1 会前草稿生成（核心）

#### 输入项

| 输入 | 是否必填 | 说明 |
|------|----------|------|
| 行业场景 | 是 | 工业视觉工控 / ICT 云安企软 / 芯片 FAE |
| 本场目标 | 是 | 摸底 Discovery / 方案沟通 / 逼近试点 |
| 客户一句话 | 是 | 行业 + 规模/背景 + 已知目标 |
| 本场补充已知信息 | 否 | 干系人、预算、交期等新信息 |
| 竞品 | 否 | 在谈厂商；空则对比客户现状手段 |
| 我方产品/方案要点 | 建议填 | 公开能力 brief；越具体，对齐与异同越有用 |
| 本场会议纪要 | 是 | 可杂乱；只贴本场新内容即可（有档案时） |
| 关联客户档案 | 否 | 从下拉或右侧名录选用 |
| 记录为一次拜访 | 否 | 关联档案时可勾选写入拜访记录 |
| 写入本地历史 | 否 | 默认开启 |
| 演示模式 | 否 | 不调大模型，返回样例，用于跑通流程 |

#### 输出：固定七段结构

| 段 | 标题 | 主要内容 |
|----|------|----------|
| 1 | 客户画像（事实 / 假设 / 缺口） | 分栏列出可确定事实、待验证假设、信息缺口及干系人线索 |
| 2 | 客户当前在做什么（As-Is） | 现状一句话、现状手段、关键步骤、谁在做、尚可之处、失败/不满点 |
| 3 | 痛点与需要的产品 | 痛点、业务影响、需求类型、建议对齐的我方能力位（草稿） |
| 4 | 我方与其他产品的异同 | 按对比维度：相同点、差异点、可强调点、需谨慎/待核实点 |
| 5 | Discovery 问题清单 | 本场建议追问的问题（验证现状、需求、竞品判断） |
| 6 | 讲解提纲 | 建议讲解顺序：痛点 → 能力 → 公司证据/Demo → 下一步 |
| 7 | 风险 / 待确认 / 下一步 | 不能乱承诺的点、会后动作、资料待补充项 |

文首固定声明：输出为草稿，须结合公司官方资料与合规要求核实；禁止在客户现场演示本工具；竞品对比不得使用未经核实的贬低性表述。

#### 证据纪律（贯穿全文）

生成内容要求对关键结论标注证据强度，例如：

- `stated`：客户明确说过  
- `implied`：可合理推断  
- `assumed`：纯假设，必须配验证问题  
- `from_our_brief`：来自我方要点，仍须复核  
- `unverified`：未核实，不可当事实讲给客户  

目的：降低误讲参数、误贬竞品、把假设当承诺的风险。

#### 生成方式

- **真实生成（live）：** 调用 OpenAI 兼容大模型接口（如百炼），结合系统提示词与场景上下文生成。  
- **演示模式（dry_run）：** 不调模型，返回内置样例，用于功能自测与流程演示。  
- 典型 live 耗时约 1～2 分钟（视模型与网络而定）。

### 4.2 客户名录（客户经营底座）

把「准备过 / 跟进过的客户」沉淀为名录，而不是只散落在聊天记录里。

#### 名录可记录的信息

| 字段 | 说明 |
|------|------|
| 客户名称 | 必填 |
| 一句话简介 | 行业 + 规模 + 目标 |
| 关键联系人 | 如质量王工、IT 周工 |
| 推进阶段 | 线索 / 摸底中 / 方案中 / 试点中 / 已成单 / 未成单 / 暂缓 |
| 备战备注 | 个人提醒、待办（如「下周约试样」） |
| 默认行业场景 | 下次生成可复用 |
| 竞品 / 我方要点 | 可复用到生成输入 |
| 累计已确认事实 | 跨拜访沉淀 |
| 开放缺口 | 仍待验证的问题 |
| 拜访列表 | 目标、场景、时间、纪要摘录 |

#### 名录界面能力

- 右侧「客户名录」列表展示：阶段、场景、拜访次数、事实数、缺口数、备注摘要  
- 搜索：按名称 / 联系人 / 备注过滤  
- **选用**：一键带入本场备战（一句话、场景、竞品、产品要点等）  
- **新建客户**：左侧表单写入名录  
- **编辑档案**：联系人、阶段、备注、事实、缺口可保存  
- **删除**：从名录移除本地档案（生成历史仍可保留）

数据仅存本机：`data/customers/*.json`（不入库到公网；已 gitignore）。

### 4.3 多访档案与合并

#### 为什么需要

客户经理与销售工程师都常见「同一客户多轮拜访」。若每次只靠记忆，容易：

- 上次已确认的事重复问  
- 未关闭的缺口忘了跟  
- 推进阶段说不清  

#### 多访机制

1. 第 1 次：新建客户 → 贴纪要 → 生成 → **合并**事实/缺口  
2. 第 2 次及以后：名录选用同一客户 → **只贴本场新纪要** → 生成时自动注入累计档案摘要  
3. 生成后再次合并：追加新事实、追加新缺口、关闭已解决缺口  
4. 可选「记录为一次拜访」，写入拜访列表与次数  

#### 合并反馈

- 成功：提示追加/关闭条数，以及当前事实、缺口总数；档案区高亮  
- 失败或无内容：明确错误/提示，避免「点了没反应」  

#### 安全设计

- 合并由使用者确认后写入，**不**由模型直接改档案，减少幻觉污染名录。  
- 客户与客户之间文件隔离；串访靠「档案摘要显式注入」，不靠聊天记忆。

### 4.4 行业场景包

同一套销售备战流程，可按客户类型选择场景包，使需求类型、对比维度更贴行业语境：

| 场景 | 典型用途 |
|------|----------|
| 工业 · 视觉 / 工控 | 检测、传感、产线相关方案沟通准备 |
| ICT · 云安 / 企软 | 安全、远程接入、企业软件类客户沟通准备 |
| 芯片 · FAE / 技术销售 | 器件与技术支持型沟通准备（轻量） |

说明：场景包是**辅助语境**，不是岗位锁定。实际使用时以「我方产品要点 + 客户纪要」为准；换产品 brief 即可服务不同产品线的会前准备。

### 4.5 预览、复制与导出

生成结果展示在输出区，支持：

| 能力 | 说明 |
|------|------|
| 预览 | 渲染后的 Markdown 排版（标题、表格、列表等） |
| 源码 | 原始 Markdown 文本 |
| 复制 | 复制全文到剪贴板 |
| 下载 .md | 保留可再编辑的源文件 |
| 下载预览 HTML | 带样式的预览页，浏览器打开即可看 |
| 下载 PDF | A4 预览排版，便于会前自查与会后复盘 |

操作有成功/失败提示（Toast）。

## 6. 端到端使用流程

### 6.1 单次拜访（可不建档案）

1. 选择场景与本场目标  
2. 填写客户一句话、产品要点、纪要  
3. 生成 → 预览手改 → 导出  

### 6.2 连续经营同一客户（推荐）

1. **新建客户**（名称、联系人、阶段、备注）  
2. 名录 **选用**  
3. 贴本场纪要 → **生成**  
4. 手改后，把核实事实/缺口 **合并进档案**  
5. 更新推进阶段（如摸底中 → 方案中）  
6. **导出 PDF** 自用  
7. 下次拜访：同一客户选用 → 只贴新纪要 → 再生成再合并  

### 6.3 与岗位工作的对应关系（口述用）

| 工作动作 | 工具对应能力 |
|----------|----------------|
| 客户经理：摸清客户、持续跟进 | 名录、阶段、多访事实/缺口、提问清单 |
| 销售工程师：方案讲解前准备 | As-Is、需求对齐、竞品异同、讲解提纲 |
| 双方共同：少漏问、少乱承诺 | 事实/假设/缺口分层、待核实标注、风险段 |

## 7. 技术实现概要

| 层级 | 说明 |
|------|------|
| 前端 | 本地静态工作台（HTML / CSS / JS），Markdown 预览、PDF 导出 |
| 后端 | FastAPI；提供生成、客户名录、历史、健康检查 API |

## 9. 明确边界（不是什么）

| 不是 | 原因 |
|------|------|
| 给客户演示的产品 | 客户现场只讲、只演示公司产品 |
| 公司官方选型 / 报价 / 竞品打击材料 | 输出是草稿，必须人工核实 |
| CRM / 自动成交 / 商机提醒系统 | 只做备战与轻量名录，不做全流程 CRM |
| 自动判定「我们一定赢」 | 只做结构化对比与准备，不下商务结论 |
| 替代试样、POC、实验室数据 | 无依据指标一律待确认 |
| 聊天记忆式「长期 AI 销售助手」 | 多访靠档案显式注入，可审计、可手改 |

## 10. 正确用法与使用纪律

1. 生成后必须**手改**：对照公司官方资料改参数、改表述。  
2. 未核实的数字、性能、价格、交期**不对外讲死**。  
3. 竞品对比只用有依据的同/异；无依据标待核实，不贬低。  
4. 合并进档案前确认：只写入已核实事实与真实仍开放的缺口。  
5. 不在客户现场打开本工具当 Demo。

## 12. 一句话收束

**销售工程师备战台**是一套服务本人销售工作的本地会前准备系统：用结构化生成看清客户现状、需求与竞品，用客户名录与多访档案支撑连续跟进，用预览与 PDF 导出方便自用复盘——让每一次客户拜访和方案沟通的准备更完整、更严谨、更可积累。

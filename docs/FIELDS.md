# 字段约定

本文定义输入、中间分析、最终输出的固定字段。生成内容必须按此结构填写；未知项写「待确认」，禁止编造具体技术参数与未经核实的竞品结论。

---

## 1. 输入字段（用户填写）

| 字段 ID | 名称 | 必填 | 说明 |
|---------|------|------|------|
| `scene` | 场景 | 是 | `vision` / `ict` / `chip` |
| `customer_one_liner` | 客户一句话 | 是 | 行业 + 规模/产线粗略信息 + 已知目标 |
| `meeting_goal` | 本场目标 | 是 | `discovery` 摸底 / `solution` 方案沟通 / `pilot` 逼近试点 |
| `known_context` | 已知信息 | 否 | 干系人、预算口径、交期等 |
| `notes` | 纪要/原文 | 是 | 会议纪要、微信记录、邮件摘要；可杂乱 |
| `our_product_brief` | 我方产品要点 | 建议填 | 你维护的能力/产品卡片摘要（公开表述即可）；用于「需要什么 → 对齐我方什么」 |
| `competitors` | 竞品列表 | 否 | 客户正在用或正在比的产品/厂商名；未知则留空，由分析标缺口 |

说明：`our_product_brief` 与 `competitors` 越具体，异同分析越可用；若为空，输出中必须列出待补充项，不得编造我方/竞品参数。

---

## 2. 证据强度（全局枚举）

| 值 | 含义 |
|----|------|
| `stated` | 客户明确说过 |
| `implied` | 侧面暗示或上下文可合理推断 |
| `assumed` | 纯假设，必须优先验证 |
| `from_our_brief` | 来自你填写的我方产品要点（仍须会前用官方资料复核） |
| `unverified` | 常见行业认知或未核实传闻，**不可当作事实讲给客户** |

---

## 3. 事实分层（客户画像用）

| 分层 | 含义 | 写法要求 |
|------|------|----------|
| `fact` | 输入中可确定 | 尽量贴近原文，可轻度改写 |
| `assumption` | 合理假设 | 必须标 `assumed`，并建议验证问题 |
| `gap` | 信息缺口 | 写清「缺什么」以及「缺了影响什么判断」 |

---

## 4. 客户当前在做什么（As-Is 卡）

描述客户**现状**，不是方案。

| 字段 ID | 名称 | 说明 |
|---------|------|------|
| `as_is_summary` | 现状一句话 | 客户现在怎么完成相关工作 |
| `current_means` | 现状手段 | 人工 / 抽检 / 已有视觉或传感器 / 竞品系统 / 未知 |
| `process_steps` | 关键步骤 | 3～7 步，能写则写，不能则标缺口 |
| `who_operates` | 谁在做 | 岗位角色；未知则待确认 |
| `what_works` | 当前尚可之处 | 有依据才写 |
| `what_fails` | 当前失败/不满点 | 尽量引用客户原话或纪要 |
| `evidence` | 证据强度 | 对整段现状判断的整体证据级别 |

---

## 5. 痛点卡

| 字段 ID | 名称 | 说明 |
|---------|------|------|
| `pain_id` | 编号 | 如 `P1`、`P2` |
| `statement` | 痛点陈述 | 一句话，客户语言优先 |
| `business_impact` | 业务影响类型 | 见下表枚举 |
| `urgency` | 紧急度 | `high` / `medium` / `low` |
| `impact_scope` | 影响面 | `high` / `medium` / `low`，并写一句依据 |
| `root_cause_hypothesis` | 可能根因 | 待验证，勿写成定论 |
| `need_type` | 产品需求类型 | **能力类型**，优先用场景包标准 ID |
| `evidence` | 证据强度 | `stated` / `implied` / `assumed` |
| `priority` | 需求优先级 | `must` / `should` / `could` / `non_goal` |

### 5.1 业务影响类型 `business_impact`

| 值 | 含义（视觉/工控语境示例） |
|----|---------------------------|
| `quality` | 质量/客诉/漏检误检 |
| `efficiency` | 节拍、人工、返工效率 |
| `cost` | 直接成本、报废、停线损失 |
| `compliance` | 追溯、审计、客户验厂要求 |
| `delivery` | 交期、产能爬坡、交付稳定性 |
| `other` | 其它（需写明） |

---

## 6. 需要的产品（To-Be 需求 → 我方对齐）

在痛点分析之后，单独给出「客户需要什么」以及「建议对齐我方什么」。

### 6.1 需求清单项

| 字段 ID | 名称 | 说明 |
|---------|------|------|
| `req_id` | 编号 | 如 `R1` |
| `need_type` | 需求类型 | 与场景包 ID 对齐 |
| `need_statement` | 需要什么 | 用产品能力语言描述（仍非具体报价型号，除非输入已给出） |
| `linked_pains` | 关联痛点 | `P1` 等 |
| `priority` | 优先级 | `must` / `should` / `could` |
| `suggested_our_offer` | 建议对齐的我方产品/能力 | 仅基于 `our_product_brief`；若无法对齐则写「我方要点不足，待补充」 |
| `fit_level` | 初判契合度 | `strong` / `partial` / `weak` / `unknown` |
| `evidence` | 依据来源 | 客户侧证据 + 是否来自 `from_our_brief` |

规则：没有 `our_product_brief` 时，仍可输出需求清单，但 `suggested_our_offer` 统一为「待补充我方产品要点」。

---

## 7. 我方 vs 竞品异同卡

按**对比维度**输出，禁止编造参数表。

| 字段 ID | 名称 | 说明 |
|---------|------|------|
| `dimension` | 对比维度 | 见场景包推荐维度；如检出稳定性、节拍、换型、集成、价格口径、交付服务等 |
| `customer_care` | 客户是否在意 | `high` / `medium` / `low` / `unknown`（据纪要） |
| `our_position` | 我方情况 | 只写 `our_product_brief` 中有的；否则「待补充」 |
| `competitor_position` | 竞品情况 | 只写输入中有的或明确标 `unverified`；禁止虚构指标 |
| `same` | 相同点 | 双方都能覆盖或客户感知无差异的点 |
| `different` | 差异点 | 差异描述 + 证据强度 |
| `how_to_talk` | 讲解时怎么用 | 可强调 / 需并列承认 / 建议回避待核实 |
| `verify_next` | 待核实 | 会前必须用官方资料或问客户确认的点 |

若 `competitors` 为空：输出「竞品未知」缺口，并生成用于打探竞品的 Discovery 问题；异同表可只填「我方 vs 客户现状手段」。

---

## 8. 最终输出结构（七段）

文首必须声明：

> 以下为草稿，需结合公司官方资料与合规要求核实后再用于客户讲解；禁止在客户现场演示本工具；竞品对比不得使用未经核实的贬低性表述。

### 8.1 客户画像（事实 / 假设 / 缺口）

| 小节 | 内容 |
|------|------|
| 事实 | 列表 |
| 假设 | 列表（带证据与待验证点） |
| 缺口 | 列表（含对现状/需求/竞品判断的影响） |
| 干系人线索 | 已知角色；未知则待确认 |

### 8.2 客户当前在做什么（As-Is）

输出一节 **As-Is 卡**（见第 4 节字段）。

### 8.3 痛点与需要的产品

1. 痛点卡列表  
2. 需求清单（第 6 节）：客户需要什么 + 建议对齐的我方产品/能力 + 契合度  
3. 汇总：`Must / Should / Could / Non-goal`

### 8.4 我方与其他产品的异同

1. 对比对象：我方（来自 brief）vs 竞品名或「客户现状手段」  
2. 异同卡列表（第 7 节）  
3. 一句话备战结论（草稿）：本场建议主打的差异点 + 必须谨慎的点（非赢单保证）

### 8.5 Discovery 问题清单

| 字段 | 说明 |
|------|------|
| 问题 | 具体可提问句 |
| 问谁 | 技术 / 工艺/质量 / 生产 / 采购 / 未知 |
| 验证目标 | 现状 / 某痛点 / 某需求 / 竞品异同某维度 |
| 优先级 | 本场必问 / 有时间再问 |

须包含：验证 As-Is、验证需求优先级、打探或核实竞品的问题（视缺口而定）。优先列出「最该验证的 3 个问题」。

### 8.6 讲解提纲

| 字段 | 说明 |
|------|------|
| 对应痛点/需求 | `P*` / `R*` |
| 能力位 / 我方产品点 | 对齐 `suggested_our_offer` |
| 相对竞品怎么讲 | 用第 8.4 的可强调差异；无核实则标待确认 |
| 证据/Demo 建议 | **公司产品侧**材料与演示，不指向本工具 |
| 讲述要点 | 2～4 条口播提纲 |
| 边界说明 | 能力边界、需 POC 才能承诺的点 |

### 8.7 风险 / 待确认 / 下一步

| 小节 | 内容 |
|------|------|
| 风险 | 技术、商务、决策、交付、竞品节奏 |
| 待确认 | 参数、试样、接口、我方/竞品未核实点 |
| 下一步动作 | 补我方产品要点、要竞品对比维度、约试样、拉专家等 |

---

## 9. 生成硬约束

1. **事实 / 假设 / 未知分栏**，不得混写。  
2. 每条痛点、关键竞品结论必须带 **证据强度**。  
3. **禁止编造**检出率、节拍、价格、交期、接口细节及竞品指标；输入没有则写「待确认」。  
4. 异同分析**不得**使用未核实的贬低竞品话术；不确定标 `unverified` 并放入待确认。  
5. 「需要的产品」优先写**能力类型 + 我方 brief 中的产品位**；具体 SKU/报价由使用者会后用公司资料确定。  
6. 不输出「请客户打开本系统」；对外一律围绕 **公司产品**。

---

## 10. 与场景包、能力卡片的关系

- 字段结构由本文定义，全场景共用。  
- 场景包提供：必问问题、标准 `need_type`、推荐**对比维度**、异议骨架。  
- `content/capabilities/` 存放你维护的我方产品/能力要点，供填入 `our_product_brief`。  
- 第一期深耕：`content/scenes/scene_vision.md`。  
- 阶段 6：`scene_ict.md`（完整）、`scene_chip.md`（轻量）。  
- 生成时按 `scene` 加载 `prompts/*_context.md`；历史归档见 `data/history/`。
